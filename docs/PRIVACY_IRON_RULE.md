# 隐私铁律

> CaseBoard 是面向律师的开源工具,**真实当事人数据 = 律师执业秘密**。
> 本文件把这块规则细到"看到一行就要立刻能判断对错"。

---

## 1. 核心原则

> **永远不要 commit 真实当事人数据到任何分支、任何位置、任何形式。**

这条原则**没有例外**。

- ❌ 不管是为了"展示一下问题"还是"做测试 fixture"
- ❌ 不管是不是已经"脱敏处理"了
- ❌ 不管是 PR commit message 还是 commit body 还是 PR 评论
- ❌ 不管是测试代码还是 mock 数据

## 2. 严禁出现的信息类型

| 类型 | 例子 | 替代做法 |
|---|---|---|
| 案件名 | "张三诉李四买卖合同纠纷" | "案件-A" / "某买卖合同纠纷" |
| 当事人姓名 | 张三、李四、王五 | "原告-A" / "被告-B" |
| 案号 | (2025)苏0115民初1234号 | 抽象成"测试案号-001" |
| 身份证号 | 32010119900101XXXX | 不出现 |
| 手机号 | 13800138000 | 抽象成"13800000000"占位 |
| 地址 | 南京市雨花台区XX路XX号 | 抽象成"某市某区" |
| 律师事务所 | "江苏漫修(无锡)律师事务所" | "某律师事务所"(注意维护者就是这个律所) |
| 法官姓名 | "王法官" | "承办法官" |
| 律师函 / 委托书 | 实际文档内容 | 完全脱敏后只留格式 |
| 聊天记录截图 | 微信/QQ 截屏 | 不截图 / 用 ASCII 重画 |
| 案件文书截图 | 判决书 / 起诉状 截屏 | 不截图 / 纯文字描述 |
| 案件分析报告 | 完整 MD 报告 | 不放 PR |

## 3. 允许出现的

- ✅ 抽象占位符:`case-A` `case-B` `party-X` `lawyer-Y` `court-Z`
- ✅ 测试 fixture 用纯虚构数据,且不能是真实案件的变体
  - ✅ `姓名: 测试用户-001, 身份证: 11010119900101XXXX` (明显虚构)
  - ❌ `姓名: 张三, 身份证: 32010119900101XXXX` (即使是虚构,看起来太真)
- ✅ UI 行为描述(不附图):
  - "首页 '重要日期' widget 显示:还有 5 天 续封 案件-A"
  - 不要附实际截图
- ✅ 错误日志:**去掉文件路径里的案件子目录名**:
  - ❌ `~/Documents/律师事务部/诉讼案件/张三案/裁定书.pdf`
  - ✅ `~/Documents/cases/case-A/文书-001.pdf`
- ✅ LLM prompt 模板:可以包含 **schema 示例** 但不要包含**真实案件片段**

## 4. 检查清单(commit 前)

```bash
# 1. grep 你的改动
cd case-board
git diff --cached

# 2. 看每一行:
#    - 有没有"张三""李四"等具体姓名?
#    - 有没有"2025苏01**民初****"这种真案号格式?
#    - 有没有身份证号格式(18位数字+最后一位 X)?
#    - 有没有手机号(11位以 1 开头)?
#    - 有没有具体地址(到门牌号)?

# 3. 全文搜索自己工作区
grep -r "身份证\|当事人\|案号" --include="*.rs" --include="*.ts" --include="*.md" .
```

**自动化检查**(建议加 CI 门禁):

```python
# scripts/contrib/check-privacy.py (TODO)
import re
PATTERNS = [
    (r'\d{17}[\dXx]', '疑似身份证号'),
    (r'1[3-9]\d{9}', '疑似手机号'),
    (r'\(\d{4}\)[一-龥]+?\d+号', '疑似案号'),
]
```

## 5. PR body 怎么写(无数据原则)

PR body 写"现象"和"修复",不写"实际数据":

**好**:
> 修复案情可视化阶段二 token 爆炸问题。
> LLM 在收到多选结果后,会在调 `save_case_visualization` 之前复述
> CaseGraph 结构(19 个 event 节点 + 18 条 precedes 边 + ...)给用户看。
> 大节点数(50+)时正文就吃光 32K 输出上限,工具还没调就被截断。

**差**:
> 修复张三(原告)诉李四(被告)买卖合同纠纷案件的可视化问题。
> 案情涉及 19 个事件、18 条前置关系,LLM 在第二阶段输出过长。

**差**(即使是"测试数据"):
> 测试用案件:张三(原告) vs 李四(被告),身份证 32010119900101XXXX。
> 这只是测试 fixture 不是真实数据。

## 6. 出现真实数据后的补救

如果不小心 commit 了真实数据,必须:

1. **立刻停止** push / PR
2. **重写历史**:`git filter-repo` 或 `git filter-branch` 删除该 commit
3. **如果已经 push 到 fork origin**:**立刻**联系维护者 + 强制 reset origin
4. **如果已经 merge 到 upstream**:**立刻**联系维护者撤 PR
5. 通知所有可能已经看过 PR 的人删本地副本

**不要试图"git revert 一下就行"** —— 历史 commit 数据已经泄露。

## 7. 测试 fixture 规则

测试代码里**不能有真实或疑似真实**的数据:

- ✅ 完全虚构: `姓名: A, 身份证: 000000000000000000`
- ✅ 明显占位: `姓名: 测试-001`
- ❌ 真实但脱敏: `姓名: 张某某, 身份证: 320**********0011`
  (虽然脱敏了但仍然透漏案件存在的事实)

## 8. LLM prompt 模板

`src-tauri/src/chat/prompts.rs` 里的 prompt 模板可以有:

- ✅ Schema 示例:`"name": "案件名称", "value": "string"`
- ✅ 指令说明:"提取以下字段..."
- ❌ 实际案件内容:不能用真实案件片段做 few-shot example

如果要做 few-shot,用**完全虚构**的小案例。
